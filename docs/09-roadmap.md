# 路线图

MVP 之后的顺序。三段，按难度递增：

**第一段 单应用能力** — 全在一个进程内，无进程边界，无一致性设计
**第二段 应用交互** — 开始拆进程，引入应用之间的数据流
**第三段 集群增强** — 同种应用横向扩

每个阶段的产物都能独立用。任何一个阶段停下来都是一个完整的东西。

---

# 第一段：单应用能力

全部在 `gateway` 单二进制内完成。不新增进程、不新增外部依赖。

## 1.1 多格式入站

**问题**：客户端 SDK 各家格式不同。用 Claude SDK 的 agent 没法打 OpenAI 模型。

**做什么**：
- 入站端点扩展：`/v1/messages`（Claude）、`/v1beta/models/*`（Gemini）、`/v1/responses`
- 转换矩阵：任意入站格式 × 任意出站格式
- `format.rs` 的 `enum Format` 从 1 个扩到 4 个
- `convert(from, to, body)` 从恒等实现变成真实的转换表
- 同格式仍走透传零拷贝路径

**新增模块**：
- `crates/protocol/src/convert/` — 每个方向一个文件（`openai_to_claude.rs` 等）
- `crates/protocol/src/dto/claude.rs`、`gemini.rs`、`responses.rs`
- `apps/cli/src/routes/` 增加对应端点（`messages.rs`、`gemini.rs`、`responses.rs`）

**数据流变化**：无。仍是 ingress → router → protocol → provider → upstream，
只是 protocol 那一步从透传变成真转换。

**难度**：低。纯函数，无 IO，能用差分测试严格验证 —— 同一批请求过转换器，
输出与手写的期望字节逐一对比。

**为什么排第一**：这是相对现成方案的核心差异点，而且风险最低。

**完成判定**：Claude SDK 打 OpenAI 渠道能通；Gemini SDK 打 Claude 渠道能通；
流式响应的 chunk 边界与格式正确。

## 1.2 多 provider

**问题**：只有 3 个 provider（openai / openai-compat / ollama），覆盖不够。

**做什么**：按实际需要逐个加 provider 实现。建议顺序：
1. `claude` — 原生 Anthropic
2. `gemini` — 原生 Google
3. `bedrock` — AWS 签名（这个最麻烦，需要 SigV4）
4. `vertex` — GCP 服务账号鉴权（需要 JWT 换 token + token 缓存）
5. 其余按需

**新增模块**：
- `crates/provider/src/<name>.rs` 一个文件一个 provider
- `crates/provider/src/auth/` — 需要动态鉴权的（Bedrock SigV4、Vertex JWT）
  单独放，因为它们有**内部状态**（token 缓存），是唯一违反"provider 无状态"的地方。
  处理办法：把 token 缓存做成 `provider` 之外的 `AuthProvider` trait，
  由 orchestrator 注入已获取的凭证，provider 本身仍然无状态

**数据流变化**：新增一条内部边 orchestrator → auth（获取动态凭证），
可能触发一次外部 HTTP（换 token）。这条边要有独立缓存与超时。

**难度**：低-中。数量多但每个都独立，错了只影响那一个 provider。

**完成判定**：每个 provider 的 `gateway test <channel>` 通过；
非流式与流式都验证；错误分类正确（key 错要熔断，参数错不重试）。

## 1.3 用量与观测增强

**问题**：JSONL + `stat` 子命令在请求量大了之后不够用。

**做什么**：
- 内存滚动窗口统计（最近 1h / 24h），`GET /metrics` 暴露
- Prometheus 格式导出（可选，配置开关）
- 慢请求采样：超过阈值的请求记完整上下游报文到单独文件，用于排障
- `gateway stat --watch` — 实时刷新
- 按渠道的健康度评分（成功率 + P95 + 熔断次数的加权）

**新增模块**：
- `crates/observe/src/window.rs` — 内存滚动窗口
- `apps/cli/src/routes/metrics.rs` — `GET /metrics` 端点
- `crates/observe/src/trace_dump.rs` — 慢请求采样

**数据流变化**：新增 stream → observe 的异步边（与 usage 那条并列）。

**难度**：低。纯本地，无外部依赖。

## 1.4 请求增强

**问题**：不同渠道对同一模型的行为有差异，需要按渠道调整。

**做什么**：
- 渠道级参数覆盖（已在 MVP 预留 `param_override`，这里做完整）
- 渠道级 header 覆盖
- 模型映射：客户端请求 `gpt-4o`，某渠道实际叫 `gpt-4o-2024-11-20`
- 请求体裁剪：某些渠道不支持某参数，自动剔除而不是报错
- system prompt 注入/覆盖（按渠道）
- 敏感词前置拦截（本地词表，可选）

**新增模块**：
- `crates/orchestrator/src/rewrite.rs` — 覆盖规则的应用点
- `crates/protocol/src/trim.rs` — 按 provider 能力表裁剪不支持的字段

**数据流变化**：protocol 那一步之前插入一个 rewrite 步骤。

**难度**：低。但要注意**顺序**：别名 → 模型映射 → 参数覆盖 → 裁剪。
顺序错了会出现"覆盖的参数被裁掉"。

## 1.5 异步任务

**问题**：图像/视频/音乐生成是"提交 → 轮询 → 取结果"三段式，与同步 chat 完全不同。

**做什么**：
- 第二个 provider trait：`TaskProvider`。它与 `Provider` **不能合并** ——
  返回类型不同（同步返回 usage，异步返回 task_id + 状态），
  生命周期不同（一次请求 vs 跨多次请求）
- 任务状态需要持久化 → **这里第一次需要本地数据库**。用 SQLite 单文件
- 轮询循环：进程内一个后台 task，定期拉取未完成任务
- 端点：提交、查询、取消

**新增模块**：
- `crates/provider/src/task/` — `trait TaskProvider` + 各平台实现
- `crates/task/` — 新 crate：提交、轮询循环、状态机
- `crates/store/` — 新 crate：SQLite，**只存任务表**（不是全量数据库）

**数据流变化**：**第一次出现内部异步流** ——
提交路径写任务行，轮询循环独立读写任务行，两者靠 SQLite 的行锁协调。
这是从"纯请求响应"到"有后台状态"的转折点。

**难度**：中。引入了持久状态和后台循环。但仍在单进程内，不涉及跨进程一致性。

**完成判定**：提交一个视频生成任务，进程重启后轮询仍能继续；任务超时能正确标记失败。

## 1.6 多用户与计费（**可选**）

只有当你要给别人发 key 时才做。自用场景跳过。

**做什么**：
- token 表（SQLite）：key、余额、可用模型白名单、过期时间
- 请求鉴权：从 bearer token 查 token 行
- 配额预扣 → 结算 → 差额退还
- 消费记录（从 JSONL 升级到 SQLite 表）

**新增模块**：
- `crates/quota/` — **配额算术唯一入口**。newtype `Quota(i64)` + `TryFrom`，
  禁止裸 `as` 转换。所有乘法先做溢出检查，饱和时返回错误而不是回绕
- `crates/auth/` — 新 crate：token 校验
- `crates/billing/` — 新 crate：预扣/结算/退款状态机
- `crates/store/` 扩展 — token 表、消费记录表

**数据流变化**：ingress 那一步之后插入 auth；
orchestrator 前后插入 billing 的预扣与结算。

**难度**：中-高。**这是唯一涉及钱的部分，错了直接是损失。**

三条不变量，从第一行代码就要立：
- **任何用户可控的量在进入配额计算前必须有上界**。请求次数、图像张数、
  视频秒数、max_tokens —— 每一个都要 reject 而不是 clamp
- **配额转换禁止裸 cast**。全部走 `quota` crate 的 checked 函数，
  饱和事件必须留审计记录
- **预扣必须在请求发出前落地，结算必须幂等**。重试不能重复扣费，
  进程崩溃后未结算的预扣要能被回收

**完成判定**：并发压测下账目对得上（`SUM(消费记录) == 余额变化`）；
构造一个超大 `max_tokens` 请求，被 400 拒绝而不是产生负数配额。

## 第一段小结

做完 1.1–1.4 就是一个完整的个人级多模型网关。
1.5 按需（要生成图像/视频才做）。1.6 按需（要给别人发 key 才做）。

**这一段的关键性质：全程单进程，没有任何跨进程一致性问题。**
配置在文件里，状态在内存或本地 SQLite 里。改配置发个 SIGHUP。

# 第二段：应用交互

只有当以下任一条成立才进入这一段：
- 单机 CPU/带宽撑不住
- 需要非技术人员改配置（要 Web UI）
- 需要多机分摊出口 IP

否则第一段就够了。**拆进程只带来运维成本，不带来功能。**

## 2.1 拆出 egress（出网代理）

**为什么第一刀切这里**：不碰计费、不碰路由、不碰任何共享状态。

**做什么**：
- 独立进程/容器跑代理协议栈（用现成的 sing-box / xray 二进制，不自己写）
- 它开一个本地 SOCKS5 inbound
- `gateway` 侧只认一个 SOCKS5 地址

**新增应用**：`egress`
**新增数据流**：
- **F-出网**：relay → egress → 外部上游。SOCKS5 承载 HTTPS，流式双向
- **F-出网配置**：谁来渲染 egress 的配置？MVP 阶段是人手写。
  等有了 control（2.2）才自动化

**难度**：低。relay 侧只是把 `reqwest::Proxy` 的地址从内嵌改成外部。

**收益**：relay 二进制不再需要链接任何代理协议栈依赖。
代理协议栈是重依赖（TUN、netlink、gvisor 之类），剥出去之后 relay 的编译时间和
二进制体积都明显下降。

**完成判定**：走代理的渠道 `gateway test` 通过；egress 挂掉时 relay 报错清晰。

## 2.2 拆出 control + web（管理面）

**为什么**：要 Web UI。配置从"编辑 TOML"变成"点界面"，配置源从文件变成数据库。

**做什么**：
- 新应用 `control`：管理 REST API + 静态文件由 nginx 托管
- 配置源切换：TOML → PostgreSQL（或继续 SQLite，看规模）
- relay 侧从"读文件"变成"读数据库 + 内存快照"
- 静态前端由 nginx 直接托管

**新增应用**：`control`、`nginx`、`web`（静态文件卷）、`postgres`
**新增数据流**：
- **F-管理**：浏览器 → nginx → control。HTTPS + JSON
- **F-前端**：浏览器 → nginx → 静态文件
- **F-配置读**：relay → postgres（启动时全量 + 定期刷新）
- **F-管理写**：control → postgres

**关键设计决定：relay 不需要会话系统。**
relay 只认 API token（一个字符串查一行），
浏览器会话（JWT / cookie / OAuth / 2FA / passkey）全部只在 control 里。
这条边界从一开始就要划清 —— relay 的依赖图里不允许出现任何会话相关模块。

**nginx 必须配的**（否则 SSE 直接坏）：
- `proxy_buffering off`、`proxy_request_buffering off`
- `proxy_read_timeout` / `proxy_send_timeout` 调到几千秒
- `client_max_body_size 0`（大附件），改由应用层限制
- WebSocket 升级头透传
- 真实客户端 IP 靠 `X-Forwarded-For` 传递，relay 侧要配可信代理，
  否则 IP 相关逻辑全部命中 nginx 的 IP

**路径分发**：`/v1/*` → relay，`/api/*` → control，`/` → 静态文件。
注意如果有 `/v1/dashboard` 这类管理端点，前缀与 relay 重叠，
nginx 要让更长前缀优先匹配。

**难度**：中。面广（管理 API 全套）但都不在热路径上。

**完成判定**：Web UI 改一个渠道，relay 在刷新周期内生效；
relay 的依赖图里不含会话模块。

## 2.3 配置失效通知

**问题**：2.2 之后 relay 靠定期轮询数据库刷新配置。
管理员在 UI 上禁用一个渠道，relay 最多要等一个轮询周期才知道。
"我明明关了它还在打" 是这个阶段最烦人的问题。

**做什么**：
- 引入 Redis，用 pub/sub 做失效通知
- control 写完事务**提交之后**发一条 `{kind, id, version}`
- relay 收到后**不信任消息内容**，只当"去数据库重读"的触发器

**新增应用**：`redis`
**新增数据流**：
- **F-失效通知**：control → redis pub/sub → relay

**这是整个路线图里唯一需要新造的分布式机制。设计要点：**

Redis pub/sub **不持久、不重传、订阅者掉线就丢消息**。所以：
1. 消息只是加速器，把典型延迟从一个轮询周期压到 1 秒
2. **必须保留定期轮询作为兜底**。任何"只靠 pub/sub 不要轮询"的设计都是错的
3. 消息里带 `version`，relay 比对本地版本决定是否重读，避免惊群
4. 收到消息后重读的是**权威源（数据库）**，不是消息内容

**难度**：中。机制本身简单，但正确性下限容易设计错。

**完成判定**：起两个 relay 实例，在 UI 禁用渠道，两个实例都在 1s 内停止选它；
手动 kill pub/sub 连接，确认轮询仍能兜住。

## 2.4 拆出 worker（后台任务）

**问题**：1.5 的异步任务轮询循环跑在 relay 进程里。
relay 多副本后，N 个副本会重复轮询同一批任务。

**做什么**：
- 新应用 `worker`：所有后台任务集中在这里
- relay 只负责"提交任务 + 写任务行"，不再轮询
- 任务去重靠数据库租约：一张锁表，任务类型作主键，
  CAS 抢锁 + 检查影响行数 + 心跳续租

**新增应用**：`worker`
**新增数据流**：
- **F-任务租约**：worker ⇄ postgres。CAS UPDATE + 心跳
- **F-主动外呼**：worker → 外部上游。渠道测活、任务状态轮询
- **F-任务提交**：relay → postgres（写任务行），worker 读

**难度**：中。租约机制要仔细：
- 租约 TTL 与心跳间隔要留至少 2 次失败余量
- **任务 handler 必须幂等**。租约过期后重跑是正常路径，不是异常
- 租约过期的任务要能被标记失败并重新抢

**完成判定**：起 2 个 worker，锁表里同一类型只有一行；
kill 一个，另一个在 TTL 内接管。

从 1 个应用变成 7 个：`relay`、`control`、`worker`、`egress`、`nginx`、`postgres`、`redis`。
新增 7 条应用间数据流。

**这一段的关键性质：每个应用仍然只跑 1 个副本。**
所有的"多副本才会暴露的问题"都留到第三段。

# 第三段：集群增强

同种应用横向扩。

## 3.1 relay 多副本

主要扩容对象。会坏的是所有**进程内可变状态**：

**加权轮询游标** — MVP 里是进程内 `AtomicUsize`。
N 个副本各自从 0 开始，导致所有副本都优先打同一个渠道，加权失效。
→ 游标移到 Redis `INCR` 取模。

**熔断器状态** — 进程内计数。副本 A 已熔断的渠道，副本 B 还在打。
→ 两种选择：(a) 熔断状态放 Redis 共享；(b) 保持副本本地，接受"每个副本各自学习"。
**推荐 (b)** —— 熔断本质是本地观测，A 到某渠道不通不代表 B 也不通
（不同副本可能在不同网络位置）。共享熔断反而会传播错误信号。

**配置内存快照** — 副本本地，靠 2.3 的失效通知 + 轮询兜底。可接受。

**可重放请求体的临时文件** — 副本本地磁盘。
只要一次请求的全部重试都在同一副本内完成就没问题。
前提：**负载均衡器不能在请求中途改路由**。

**连接池** — 副本本地，无跨请求语义，不用管。

**如果做了 1.6 计费**，这里是最危险的部分：
- 配额扣减必须是数据库单行原子操作（`UPDATE q = q - ?`），
  **不能读改写**。读改写在多副本下必然丢更新
- 任何"进程内累加、定期批量落库"的优化在多副本下都是错的 ——
  N 个副本各攒各的，落库时互相覆盖。要么不做这个优化，要么累加放 Redis

**完成判定**：多副本并发压测，账目对得上；
加权轮询在副本间整体符合权重比例。

## 3.2 worker 多副本

2.4 的数据库租约已经支持，基本零改动。

唯一要检查的：**有没有任务没走租约**。
凡是"启动时直接起一个循环"的任务，多副本下都会重复执行。
全部纳入租约体系，不留例外。

**完成判定**：kill 一个 worker，未完成任务在 TTL 内被另一个接管，不重不漏。

## 3.3 control 多副本

要处理三件事：

**数据库迁移必须单点**。两个副本同时跑迁移会并发 `ALTER`。
→ 独立的 init 容器，或用数据库的 advisory lock。**不要用环境变量选主** ——
配错了就是两个都迁移或都不迁移。

**支付/外部回调幂等**。回调入口通常无鉴权，
任一副本都可能收到重复回调。→ 按外部订单号加唯一约束。

**权限策略最终一致**。每副本内存快照，靠轮询刷新。
放宽权限延迟生效可接受；**收紧权限有一个轮询周期的窗口**，
安全敏感的操作要配合 2.3 的失效通知立即广播。

会话本身天然安全 —— 在数据库 + Redis 里，不在进程内。

## 3.4 egress 多节点

k8s DaemonSet，每节点一个。relay 连本机 egress，出网流量不跨节点。

**这也是分摊出口 IP 的手段** —— 扩 egress 节点数直接增加可用出口 IP 数量。

安全：SOCKS5 inbound 不要暴露到集群外。它通常是无认证的，
暴露出去等于开放代理。

## 3.5 数据层

**postgres** — 主从 + 读写分离。relay 的配置读走从库，
control 的写走主库。注意 2.3 的失效通知发出后，
relay 从从库重读可能读到旧数据（复制延迟）→ 失效通知里带 `version`，
读到的版本低于消息里的版本就重试。

**redis** — 单实例够用。它只存缓存 + 轮询游标 + 失效通知，
挂了会降级（轮询兜底、游标重置）但不丢数据。
不要为它上 Cluster，复杂度不值得。

**日志/用量数据** — 写入量最大的部分。
到这一步可以考虑独立数据库（或列存），与主库分开。
先把写入改成**异步批量**，稳定之后再考虑换引擎。**不要一次动两件事。**

# 全程贯穿的两条约束

## 依赖图强制纯度

`crates/protocol` 与 `crates/provider` 永远不允许依赖 `store` / `cache` / `upstream`。
它们是纯函数：输入请求出请求，输入响应出 usage。

CI 加检查：`cargo tree -p provider` 的输出里不出现 `sqlx` / `redis` / `reqwest`。

**从 MVP 第一天就立好。** 等到第二段再补就晚了 ——
那时已经有一堆越界依赖要拆，而且拆的时候你会发现"顺手在 provider 里查一下数据库"
这种事已经写了几十处。

## 配额算术唯一入口（做了 1.6 之后）

`crates/quota` 是唯一允许做配额数值转换的地方。
newtype 包装，禁止裸 cast，所有乘法先查溢出，饱和留审计。

用户可控的量（次数、张数、秒数、token 上限）在进入计算前必须有上界，
**reject 而不是 clamp** —— clamp 会让用户以为请求成功了但拿到的不是他要的。

# 优先级总结

只做一件事：**MVP**（见 `08-mvp.md`）。它已经能替代现成方案的 agent 用法。

只做三件事：**MVP → 1.1 多格式 → 1.3 观测**。
这三个全在单进程内，覆盖 agent 自用的全部需求，零运维负担。

**不要跳到第二段**，除非单机真的撑不住。
从 1 个进程变 7 个进程，功能不增加一点，运维成本翻好几倍。

三段的分界线：
- 第一段：单进程，配置在文件，**无任何一致性设计**
- 第二段：多进程各 1 副本，引入失效通知（唯一新机制）
- 第三段：同种应用多副本，主要工作是消灭进程内状态
