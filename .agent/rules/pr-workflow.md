# PR 开发流程（主控与子代理协作）

**什么时候读这份文档**：要开一个 PR 干活的时候——尤其是要派子代理（subagent）来分担任务的时候。

**这份文档解决什么**：一个 PR 从建分支到合并的完整流程。核心是：主控负责拆任务、派活、审查产出，
不亲自把实现写完；每个子任务都要有可复验的证据。

---

## 一、遇到什么问题（含曾经踩过的坑）

| 你看到的现象 | 真正的原因 | 后果 |
|---|---|---|
| 主控自己把代码全写了 | 没有拆任务、没有派子代理 | 子代理形同虚设，产出没人独立审查 |
| 子代理把文件写到了仓库根目录或别的 worktree | prompt 里只给了相对路径，子代理自己推导错了位置 | 污染其他会话的工作区 |
| 一个子代理要干半个模块 | 任务没拆够 | 产出没法验收，只能返工 |
| 到最后才发现问题 | 只在收尾时做了一次审查 | 修复成本随问题堆积指数上升 |
| worktree 里出现了嵌套的另一层 worktree | 创建 worktree 时人不在仓库根目录 | 曾经发生过 13 层嵌套、321G 重复编译产物的事故 |

---

## 二、维护者希望做什么事

你是**主控**：编排任务、派子代理执行、审查子代理的产出。**不要亲自把核心实现写完。**

- 所有工作面都登记为 PR；子任务用 checkbox 记到 PR 正文的任务清单里，完成后勾掉。
- 每完成一轮"审查加修复"，在 PR 下写**一条**评论（包含修复的 commit 号）。
- 冒烟验证（smoke test）单独再写**一条**评论，说明用的方法和结果。
- 难以确定的地方和风险点写进 PR 正文对应字段，不要写进完成标准里。
- 开发目标的登记与 PR 正文的任务清单全程保持同步。

---

## 三、可能的情况（九个阶段）

### 阶段 0：准备

- 从目标分支拉新分支，工作目录放在 `.wt/<分支名尾段>/`，不要在仓库根目录改代码。
  例：分支 `feat/admin-api` 对应目录 `.wt/admin-api`。
- 创建 draft PR。标题用约定式提交格式（如 `feat(web): ...`），正文包含：目标、范围、任务清单、验收命令。
- 开工前查一下最近 24 小时内有没有相关的 PR 或会话在跑；工作面重叠就停下来问维护者。
- 登记开发目标（omp 的 `todo` 工具或 goal 命令——把你这个 PR 的目标和阶段逐条登记进去），
  主控和子代理全程对照，偏航立即纠正。
- 记录下来 `base_sha`，后面做 CRG 和 review 时用 `--base <base_sha>`，不要写死 `main`。

**worktree 创建硬规则**（必须遵守，防止嵌套事故）：
1. 必须先 `cd /home/hathaway/projects/ferrite`（仓库根），再执行 `git worktree add .wt/<名字> -b <分支>`。
   `git worktree add` 的相对路径是按**当前所在目录**解析的——如果人在某个 worktree 里面，新目录会落到那个 worktree 里形成嵌套。
2. 创建后必须自检：`git worktree list` 里新条目的路径应该是 `/home/hathaway/projects/ferrite/.wt/<名字>`。
   如果路径里出现了两个 `.wt/`，说明嵌套了，立刻 `git worktree remove` 撤销重来。
3. 闸门有 `checklist_no_nested_worktree` 检查项，会在提交 / 推送 / 合并时扫描，命中直接 FAIL。
4. 派子代理时，prompt 里必须写**全局绝对路径**（例如 `/home/hathaway/projects/ferrite/.wt/<名字>/`），禁止让子代理自己推导相对路径。

### 阶段 1：摸清范围

- 跑一次 `code-review-graph update` 建立代码图谱。
- **修改导出的符号之前，必须先查它的调用方**（用 codegraph 查，本地没有 LSP）。
- 找出这次要改的模块、它的调用方、被调用方、以及相邻的边界。
- 产出：难以确定的地方（写进 PR 正文）、风险点、可能波及的文件清单。

### 阶段 2：拆任务

- 先按文件拆；同一个文件内再按修改范围拆；还是太大就按主题 / 调用链 / 测试来拆。
- 每个子任务必须写清楚：全局绝对路径的工作目录、允许改哪些文件、禁止碰哪些文件、目标、非目标、验收命令。
- **开发必须带测试**：新功能或修复要在同一个 PR 里补测试，尽量覆盖正常路径、边界、错误输入、并发重入。
  当前没法覆盖的情况，用 `todo!("TODO(#N): 场景说明")` 显式声明缺口。
  测试代码也要写注释：说明测的是什么行为、为什么是这个预期。
- 不要相信子代理会自己做完：每个子任务都要有主控能复验的文件边界和验收证据。
- 子任务太大、文件边界不清楚、或者需要跨模块协调，就继续拆。禁止让一个子代理干完半个模块。

### 阶段 3：开发与审查循环

```text
重复以下循环：
  开发 → 派子代理执行划分好的任务，最多同时并行 2 个互不冲突的子任务；
         同一文件或同一模块的写入必须串行
  审查 → 子代理完成后，主控独立校验：
         · 真的跑一遍子代理给的验收命令（不只看它的输出）
         · 看 diff，确认改动只落在它声明的文件里
         · 检查根因、调用方、边界输入
         · 必要时再派一个子代理做交叉确认
  失败 → 重新拆任务，或者打回去重做
```

### 阶段 4：测试

- 全部子任务通过审查后，本地只跑极小范围的类型检查：`cargo check -p <包名>`，必须套 `cpulimit -l 65 -i --`。
- 集成测试、多 crate 联调、重型测试（超过 2 分钟、需要容器或网络）全部推到 PR，交给 CI 按改动内容动态执行。
- CI 报错时，拉取云端的失败日志，当作新任务修复。拉法：打开 PR 页面的 Checks 标签 →
  点进失败的 job → 复制报错段落；或用 `gh run view --log-failed`。
- **注意**：新增的测试要确认 CI 真的会执行它。有三个静默失效模式（feature 门禁、e2e 无数据库、
  `#[ignore]`）——详见 `.agent/rules/testing-ci.md`。

### 阶段 5：工具审查

- 先做结构层审查：`code-review-graph detect-changes --base <base_sha>`
  （`base_sha` 是你开 PR 时记录的基准 commit 号，即分支从哪个 commit 拉出来的那个点）
- 再做规范层审查：`ocr review --from <base_sha> --to HEAD`
  （`ocr` 是代码审查工具，不是截图识别；要按模块、按 PR diff 分块喂——比如一个 crate 一个 crate 地喂，
  不要一次性把整个仓库的 diff 都喂进去，会触发限流）
- 发现问题就回到阶段 3 修复，然后重新审查，直到干净。
- 每轮"审查加修复"在 PR 下写一条评论，包含：发现的问题、修复的 commit、验证命令。

### 阶段 6：冒烟验证

- 按真实用户路径跑一遍：命令行命令、真实 URL、真实进程。UI 用截图或 OCR 对比。
- 发现问题：更新 PR 任务清单，回到阶段 3 做二次修复。
- 通过后，在 PR 下写一条评论："冒烟验证通过 / 用的方法 / 结果"。

### 阶段 7：清理

- **先跑闸门复检**：`gate pre-commit` 和 `gate pre-push`，FAIL 清零后再做下面的事。
- **文件清理**：检查分支目录里有没有和本次开发无关的杂物（旧脚本、临时文件、废弃产物）。
  要么加进 `.gitignore`，要么用 `gio trash` 移进回收站。**严禁用 `rm` 或 `git clean` 永久删除。**
- **代码清理**：测试代码没放在 `tests/` 目录的挪过去；跑格式化工具；清掉调试日志、注释掉的代码、
  调试用的替身代码；更新和实现不一致的文档注释。
  如果格式化工具改了文件，必须重跑最小验收命令、工具审查、冒烟验证，并更新 PR 评论。
- **文档同步**：更新改动的代码注释，以及 `AGENTS.md`、`README.md`、`docs/` 里过期的段落，引用要保持一致。

### 阶段 8：汇报

- 汇报内容：改了哪些文件、跑了哪些测试、CRG / ocr / 冒烟验证的结果、PR 链接、剩余风险。
- **收尾报备**：列出这个会话新建或修改的全部 PR。有新建但没报备的就是违规。

## 四、约束事项（硬性门禁）

- **只能通过 PR 干活**：所有工作面都要登记为 PR。禁止新建 GitHub issue，禁止改动 epic 结构
  （挂载或摘除子 issue）。只有维护者在对话里明确要求建 issue 时，先报告标题和完成标准，批准后再建。
- **工作目录门禁**：所有子代理必须在 `.wt/<分支名>/` 目录里工作。
  子代理 prompt 必须写明全局绝对路径和所属分支，限定它只能在该目录里读写、编译、提交。
  禁止在仓库根目录或其他 worktree 里落文件。
- **任务量门禁**：单个子任务不超过 5 个文件、单一主题、单一修改范围。
- **不绕过闸门**：不绕过 `.githooks/` 的拦截，不绕过 `hooks/merge --dry-run` 预检。
